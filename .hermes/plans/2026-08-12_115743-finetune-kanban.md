# Finetune Pipelines — Kanban Board Plan (Hermes /kanban)

> Companion to `2026-08-12_115150-finetune-pipelines.md`. This document turns the
> stream-based implementation plan into a durable Hermes Kanban board so Scott can
> track progress across the parallel research streams from one surface.

**Goal:** A single SQLite-backed kanban board (`finetune`) that encodes all research + build + candidate-case work, with the parallel streams modeled as independent cards, the cross-stream synthesis as a verifier/synthesizer gate, and the build/case/expansion phases as a parent→child dependency chain — so status is visible via `hermes kanban list`/`stats`/`watch` at any time.

**Architecture of the board:**
- One board per workstream. This project uses board slug `finetune`.
- The **research phase** (Stream O online + Stream R repo-analysis) is modeled as a **Kanban Swarm** (parallel worker cards → verifier → synthesizer), which is exactly the tool for "8 tasks in parallel, then a synthesis memo."
- The **build + candidate case + expansion** phases are plain tasks linked into a dependency chain with `link parent_id child_id`.
- Each card carries an **assignee profile**, **priority**, optional **model/provider override**, **idempotency-key** (safe re-run), and an optional **skill** hint.

**Tech:** Hermes `kanban` CLI (SQLite `kanban.db`), profiles as workers, dispatcher in gateway, `link` for dependencies, `swarm` for the parallel research graph. No new tooling.

## Board lifecycle & status model

Statuses a card moves through (driven by CLI verbs): `triage → todo → ready → running → review → done`, plus `blocked` and `scheduled`. The dispatcher (running in the gateway by default) promotes `todo→ready`, atomically claims `ready` cards, spawns the assigned profile, and returns them to `review`/`done`.

Tracking commands — **board flag comes BEFORE the verb** (`--board finetune ls`, NOT `ls --board finetune`):
- `hermes kanban --board finetune ls` — the whole board: card id, status, assignee, title.
- `hermes kanban --board finetune stats` — per-status + per-assignee counts + oldest-ready age.
- `hermes kanban --board finetune show <id>` — one task's comments + events.
- `hermes kanban watch` — live-stream events (Ctrl+C to exit).
- `hermes kanban --board finetune tail <id>` — follow one task's event stream.
- `hermes kanban --board finetune notify-subscribe <id> --platform telegram --chat-id 8671602066 --chat-type dm` — push a task's terminal events (incl. completion) to Telegram.
- Reading the board: ▶ = ready/in progress, ◻ = todo (waiting on a dependency above it). Each line = `id  status  assignee  title`.
- Current-board default: `hermes kanban boards switch finetune` makes plain `hermes kanban ls` work without `--board`; otherwise pass `--board finetune` every call. (Do NOT switch Scott's default away from `default` without being asked.)
- Completion updates: all cards are subscribed to Telegram (SR Patterson, id 8671602066) via `notify-subscribe`. Marking a card complete (`hermes kanban --board finetune complete <id>`) pushes an update to Scott.

**Slash-command access:** in a Hermes chat session use `/kanban ...` (same verbs, board flag before verb: `/kanban --board finetune ls`). The kanban toolset (`kanban_list`, `kanban_show`, etc.) is available to profiles that enable it; dispatcher-spawned workers get the focused `kanban_*` toolset gated by `HERMES_KANBAN_TASK`.

## Stream S / RESEARCH PHASE — ONE SWARM GRAPH

The research phase is a single `swarm`: 8 parallel worker cards (5 online + 3 repo-analysis) → a verifier → a synthesizer that writes the design memo. This encodes "online tasks in parallel, repo tasks in parallel, then synthesis" as an actual dependency graph the dispatcher honors.

```
hermes kanban swarm \
  --board finetune \
  --goal "Produce the finetune design memo (docs/design.md + configs/tasks.yaml + configs/providers.yaml) by synthesizing 8 parallel research memos." \
  --worker default:O1_adaption:"" \
  --worker default:O2_model_provider_matrix:"" \
  --worker default:O3_jetson_local:"" \
  --worker default:O4_harness_integration:"" \
  --worker default:O5_weights_registry:"" \
  --worker default:R1_elite_agents:"hermes-agent" \
  --worker default:R2_prior_finetune:"" \
  --worker default:R3_unai_panel_data:"" \
  --verifier default \
  --synthesizer default \
  --idempotency-key finetune-research-swarm-v1
```

If preferred, each worker card can carry a `--model` override (e.g. a cheap model for online research, a stronger one for synthesis). Worker cards default to profile `default` (this profile); adjust to a dedicated worker profile if Scott sets one up.

Each worker card maps to its memo:
| Card | Memo |
|---|---|
| O1_adaption | `research/online/adaption-labs.md` |
| O2_model_provider_matrix | `research/online/model-provider-matrix.md` |
| O3_jetson_local | `research/online/jetson-local.md` |
| O4_harness_integration | `research/online/harness-integration.md` |
| O5_weights_registry | `research/online/weights-registry.md` |
| R1_elite_agents | `research/repos/elite-agents.md` |
| R2_prior_finetune | `research/repos/prior-finetune.md` |
| R3_unai_panel_data | `research/repos/un-ai-panel-data.md` |

The synthesizer card produces `docs/design.md` + `configs/tasks.yaml` + `configs/providers.yaml` (Stream S of the implementation plan). A verifier card sits between the 8 workers and the synthesizer, blocking synthesis until the 8 memos exist and pass a completeness check.

## Modeling the parallelism explicitly

The reason to use a board (vs a flat todo list) is the **dependency edges**:

- **Research parallelism:** the 8 swarm workers have no edges between them — all are `ready` immediately; the dispatcher runs them in parallel (capped by `delegation.max_concurrent_children`). The verifier waits on all 8; the synthesizer waits on the verifier.
- **Cross-stream independence:** Stream O and Stream R are independent — none of R1–R3 blocks O1–O5, so both streams run simultaneously.
- **Build vs research:** build cards have no dependency on research memos *in the card graph*, but in practice they should not be dispatched until the synthesizer card completes (S = design memo). Enforce this by **blocking** B0 until S is done: `hermes kanban block <B0_id>` then `hermes kanban unblock <B0_id>` after the swarm lands. Alternatively set the synthesizer as the parent of B0.
- **Expansion gating:** D1–D4 all `--parent <C5_id>` so they stay `todo` (parents open) until C5 completes.

This gives Scott a true progress view: `hermes kanban stats --board finetune` shows 8 research cards, then the verifier, then the synthesizer, then the B→C→D chain with ready-age and assignee counts.

## Daily / per-session tracking workflow

1. Open the board: `hermes kanban ls --board finetune` (or `/kanban ls` in chat).
2. See what's stuck: `hermes kanban stats --board finetune` (oldest-ready age surfaces stalled cards).
3. Optionally get live/phone updates: `hermes kanban watch` in a terminal, or `hermes kanban notify-subscribe <id>` to route a card's terminal events to Telegram (via the gateway) so progress surfaces on Scott's phone without polling.
4. When the dispatcher is enabled (runs in gateway by default), `todo`/`ready` cards auto-claim and run; Scott only intervenes to `unblock`, `promote`, `reassign`, or set `--model` overrides.
5. Mirror memos/reports to the JetsonVault as they land (`cp research/**/*.md C:/Users/spatt/Desktop/JetsonVault/projects/finetune/`) — keep that step a note on each synthesizer/complete event or a small cron.
